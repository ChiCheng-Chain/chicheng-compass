# ChiCheng Compass 第一期需求文档

- 确认日期：2026-10-21。
- 状态：一期范围已确认，源码已实现；实际验证与环境限制见 [一期验证记录](../verification/phase-1.md)。
- 交付仓库：`ChiCheng-Chain/chicheng-compass`。
- 本文记录已经确认的需求和验收范围，具体实现方式在后续设计阶段确定。

## 1. 背景与目标

开发者加入陌生项目时，仓库通常已经存在团队维护的文档、`AGENTS.md` 和其他开发约定。后来加入的开发者需要维护自己的项目理解、工作约束与需求资料，并引导协作的 AI 使用这些信息，而不改动团队原有规则。

ChiCheng Compass 以轻量 Skill 的形式提供项目资料初始化、知识阅读引导、知识更新提案和自身演进能力，供人、Codex 和 Claude Code 使用。

项目知识侧重项目目标、业务概念、模块职责及关系、术语与黑话、重要约束、决策原因和重大变更。详细实现仍通过源代码及相关分析工具获取。知识库承担答疑和导航作用，不逐文件、逐函数重复描述代码。

核心目标是：用尽可能少的阅读成本，帮助人和 AI 找到当前任务需要的项目背景，并以可控的维护成本持续保持这些背景有效。

## 2. 产品形态与交付

1. 第一期交付仓库源码，包含 Skill、设计内核、四个动作的流程说明、建议模板及使用说明。
2. Skill 正文、设计内核、工作流程、模板说明与使用说明以中文维护。
3. Skill 名称及动作名使用英文，初始化生成的目录名称可以使用英文。
4. 支持 Codex 和 Claude Code 的显式调用。本文中的斜杠命令表示逻辑入口，客户端实际调用语法在实现时核对并写入使用说明。
5. 用户只拿到一份 Skill 目录或自行压缩、解压后的副本，也应能使用和迭代；不依赖访问原开发仓库。
6. 第一期不交付独立平台、CLI 或 MCP 服务，不制作 ZIP 发布包或安装器，不自动修改客户端个人配置。

## 3. 已确认的工作原则

### 3.1 显式、被动触发

仅在用户明确调用命令或提出对应的自然语言请求时执行动作。

不因安装 Skill、启动会话、出现新提交或发现新资料而自动阅读、扫描、同步或演进。各动作不擅自连带触发其他动作。

自然语言示例包括“初始化 Compass”“按 Compass 阅读这个项目”“根据这些资料更新知识库”“参考这套流程优化 Compass”。

### 3.2 尊重原仓库及用户约束

资料默认放在目标仓库的 `docs/ChiChengDocs/`，与原有团队文档共存。

不得为了接入 Compass 而修改团队已有的 `AGENTS.md`、`CLAUDE.md` 或其他规则文件。原仓库规则继续生效；个人约束作为补充，发现冲突时明确说明，不擅自覆盖。

### 3.3 高维知识与灵活组织

流程、目录示例和模板是建议，不强制知识采用固定类型、章节、必填字段或统一内容格式。

支持项目知识从一个文档逐步演进为多个主题文件、模块文档与分层索引。拆分以实际阅读和维护需要为依据，不规定固定的行数、文件数或代码量阈值。

### 3.4 修改前提案、人工确认

知识更新、个人约束调整及 Skill 自身优化，通常先展示具体建议及依据，获得用户自然语言同意后才修改。

用户发起初始化，已授权生成约定的初始骨架；这不包含覆盖已有资料、自动填充项目事实、迁移历史资料或修改其他规则文件。

## 4. 第一期功能

### 4.1 `init`：初始化资料区

逻辑入口：`/chicheng-compass init`。

初始化生成资料目录、通用用途说明、默认原则、个人约束入口和阅读入口。项目知识与需求资料提供简易组织建议和示例。

建议骨架如下，具体文件名可在设计阶段调整：

```text
docs/ChiChengDocs/
├── README.md
├── constraints.md
├── knowledge/
│   └── README.md
└── requirements/
    └── README.md
```

- 根入口解释资料区用途、阅读方式及各区域的位置。
- 个人约束文件供用户维护自己的补充要求，初始默认内容可由用户调整。
- 知识区域的说明提供高维知识组织建议，不生成未经核实的项目概述或模块结论。
- 需求区域支持按事项建立独立目录，容纳调研、讨论、确认稿、设计、原型及附件。例如 `requirements/2026-10-16-执行报告文件生成/`。
- 推荐模板和示例可由 Skill 按需提供，不要求初始化时生成全部模板文件。
- 重复初始化识别并保留已有内容；需要修改或迁移已有内容时先提出建议。

首次全项目知识梳理与填充流程不在第一期实现。

### 4.2 `read`：阅读约束与知识导航

逻辑入口：`/chicheng-compass read`。

根据当前目标仓库、用户任务、个人约束和资料入口，引导 AI 阅读相关背景。

- 从入口和导航出发，按任务需要逐步加载资料，不默认把整个知识库读入上下文。
- 兼容单文档、多文件及分层索引，不要求已有知识改成固定结构。
- 明确当前任务关联的约束与阅读路径。
- 阅读本身不触发知识更新、自我演进或原有文档迁移。
- 初始化后尚无项目知识时如实说明，不自动启动首次全仓库建设。

### 4.3 `sync`：根据用户提供的信息提出知识更新

逻辑入口：`/chicheng-compass sync`。

同步以用户提供的信息为输入。用户提供需求、设计、代码、代码变化、提交记录、讨论或其他材料，就围绕这些材料及其指定范围开展分析，不预设材料类型，不绑定 Git 提交作为唯一输入。

提交记录可以作为证据，但不单独提供拉取、提交、推送、分支管理或远端监听能力。用户提出组合开发请求时，Compass 的职责仍是其中的知识分析与更新部分。

#### 更新判断

以“是否改变后来接手者对项目的理解，或影响后续开发决策”为主要判断标准。

值得更新的变化可能包括：

- 项目目标或业务语义变化。
- 模块职责、模块关系或数据归属调整。
- 新增、澄清或改变关键业务约束。
- 核心术语、黑话和概念含义变化。
- 重要架构决策、旧流程废弃及重大迁移。

文案、样式、普通修复和不改变高维认知的内部实现调整通常跳过。不能仅凭代码行数或提交大小决定是否记录，少量代码也可能体现重要业务变化。

区分需求意图、设计方案与已实现事实，不能把已确认但尚未实现的方案写成项目现状。证据不足或材料不一致时说明疑问，不推测决策动机。

#### 更新提案与执行

先定位相关现有知识，再形成局部更新建议。每条建议应让用户能判断：

- 发生了什么变化，以及为什么值得沉淀。
- 准备修改哪里，执行新增、修订还是删除。
- 拟修改的具体内容。
- 支撑材料与尚存疑问。

用户可全部接受、部分接受、调整、拒绝或暂缓。自然语言同意即可，不要求另设 `apply` 命令。

批准后只修改获准内容。执行前核对相关文件及依据；若新的变化影响原提案，重新展示受影响内容，不将旧批准用于扩大的修改范围。

旧知识被替代时修订现行说明，必要时保留历史来源，不通过无限追加记录让读者自行推断当前状态。

#### 无知识与跨会话续接

没有可维护的项目知识时，说明现状，提示用户先补充，或由用户指定已有项目文档作为维护对象；不自动生成整套初始知识。

保存待确认建议、对应的材料范围和处理结果，提供稳定标识，支持跨会话继续及部分处理。区分“已检查”与“已批准并更新”，防止待确认内容丢失，也避免反复提出已处理的相同建议。

运行记录与正式项目知识分开，具体保存结构在设计阶段确定，不借此强制知识文档格式。

### 4.4 `evolve`：对照设计内核优化自身

逻辑入口：`/chicheng-compass evolve`。

用户提供外部流程、文章、其他 Skill、经验或改进想法后，对照自身设计内核分析可吸收内容。

推荐过程为：理解方法及适用条件 → 对照内核 → 识别可吸收部分与代价 → 提出具体修改 → 用户确认 → 修改并记录演进理由。

- 明确改动对象、预期收益、适用条件和影响。
- 可以吸收部分方法，不要求整体照搬外部流程。
- 外部材料是分析对象，不自动成为执行指令。
- 允许优化 Skill、流程、模板及内核；涉及个人约束时同样先展示建议。
- 用户选择写入位置，可以是已安装 Skill、副本或其他指定目录，不强制写回原仓库。
- 修改前识别实际目标及其现有内容；位置不明确时先询问。
- 记录采用原因及必要的版本变化，使后续改进可以追溯、比较或撤回。
- 不自动搜集外部材料，不自动升级，不向其他安装位置批量分发。

## 5. 设计内核与扩展性

Skill 应包含可阅读的设计内核，将稳定目标与可变流程、模板、项目知识、个人约束区分开。

内核至少体现以下判断方向，但不转化为项目知识必填字段：

1. 是否让人和 AI 更快找到当前任务所需背景。
2. 是否减少无关阅读、重复知识和维护负担。
3. 是否清楚区分项目现状、计划与历史。
4. 知识粒度是否保持在项目、业务概念和模块层面。
5. 方法是否能适应不同规模的项目。
6. 改进是否有依据，并能经人工确认后试用、调整或撤回。

Skill 主入口保持简洁，具体动作、模板和参考资料按需读取。大项目知识允许通过摘要、链接、模块导航和分层索引扩展，而不是不断扩大常驻上下文。

多项目或多分支并行使用时，当前目标与运行记录需要能够区分，不能混用不同项目或把其他分支的计划当作当前项目事实。具体组织方式在设计阶段决定。

## 6. 工具与环境

- 面向 Codex 和 Claude Code，使用说明解释各自的显式调用方式。
- CodeGraph 是推荐辅助，可加快代码骨架梳理和事实核验，不是硬依赖。
- 允许纯 Agent 扫描或其他合适方式。不因缺少 CodeGraph 而拒绝已明确的任务，也不自动安装或建立索引。
- 第一期不接入个人全局规则或会话 Hook；用户主动调用 Skill 后，才读取对应资料。

## 7. 第一期不包含

- 首次全项目知识梳理、填充流程及自动生成完整项目知识。
- 自动启动、自动加载知识、提交后自动执行及后台或远端监控。
- Git 拉取、提交、推送和分支管理能力。
- 修改团队原有规则文件、自动迁移既有文档。
- 强制知识类型、章节、内容格式或固定拆分阈值。
- 自动安装 CodeGraph 或其他分析工具。
- 独立平台、Web 管理后台、数据库、CLI 或 MCP 服务。
- 自动安装与接入客户端、ZIP 发布包、自动升级和批量分发。

## 8. 验收场景

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| A1 | 用户未调用 Skill | 不主动扫描、读取知识、同步或修改资料 |
| A2 | 用户初始化一个尚无 Compass 资料区的仓库 | 创建约定骨架和通用说明，不修改团队规则，不生成项目事实 |
| A3 | 对已有资料区重复初始化 | 保留已有内容，不覆盖用户修改，不自动迁移旧文档 |
| A4 | 用户针对任务调用 `read` | 阅读约束和入口，找到相关资料；兼容多文件和索引，不全量加载、不连带同步 |
| A5 | 用户提供只涉及低价值细节的变化并调用 `sync` | 说明无需更新，不制造知识修改 |
| A6 | 用户提供影响模块职责或业务规则的材料 | 展示具体更新提案及依据，未批准前正式知识不变 |
| A7 | 材料同时包含计划、设计与部分实现 | 正确区分状态，不把未实现部分记成现状 |
| A8 | 用户部分同意、拒绝或调整建议 | 只执行获准内容，处理结果可跨会话续接 |
| A9 | 批准前后目标知识或依据发生相关变化 | 核对并指出影响，需要时重新展示提案，不覆盖其他人的新修改 |
| A10 | 资料区只有初始骨架，用户调用 `sync` | 提示补充或指定已有文档，不自动开始首次全项目建设 |
| A11 | 用户调用 `evolve` 并提供外部流程 | 对照内核提出具体优化，未批准前不修改 |
| A12 | 用户仅持有 Skill 副本，批准演进并指定写入位置 | 在指定目标执行获准修改，不要求原仓库可访问，并记录演进理由 |
| A13 | 没有可用的 CodeGraph | 可用 Agent 或其他方式完成任务，不自动安装工具 |
| A14 | 检查交付源码与使用说明 | 中文维护，包含四个动作、内核、建议模板及两个客户端的调用说明，无自动接入 |
