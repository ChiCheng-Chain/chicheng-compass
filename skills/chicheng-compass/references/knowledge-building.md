# 推荐的首次知识建设流程

流程修订：2026-10-22 · 代码职责范围与按需导航。

用户在 `init` 中明确要求扫描项目、建立知识库时，按需参考本指南。只说“初始化”仍只生成骨架；本指南不自动启动扫描或工具安装。

这是一条推荐路径，用户可以调整顺序、跳过步骤、缩小范围或采用自己的方法。模块划分、文档组织、工具选择和研究报告都没有强制模板。无需额外安装 research 或 domain-modeling Skill。

## 面向接手者的目标

让陌生的人或 AI 按“项目做什么 → 哪个业务模块负责 → 依赖和影响谁 → 从哪些代码开始”理解并定位。来源清单用于追溯结论，不能代替开发导航；只有源码注意事项、文件列表或宽泛业务域，而没有可定位的功能模块，还不足以达到这个目标。

以下是推荐流程的质量检查方向，不是固定章节或必填结构；材料不足的部分标明未知及下一步核验入口，不为凑齐结构编造结论。

## 主 Agent 先粗扫

先阅读仓库规则、顶层说明、主要入口、技术配置及已有文档导航，形成初步模块地图：项目服务谁、解决什么问题、主要使用场景及业务主线、有哪些可独立定位的模块、模块关系、主要依赖及待查问题。以当前实现核对旧说明；不把产品规划或设计样例当成当前业务。先让主 Agent 对项目有全局认识，再分派深入研究。

模块按业务能力或明确的技术职责划分，而不是按 Router、Service 等代码分层划分。大业务域下列出能对应实际任务的功能模块；一个模块可以跨多个目录，一个公共能力也可以被多个模块共享。粗扫时先找到各模块的候选代码入口，不把“之后去看总路由表”当成最终定位结果。

粗扫保持轻量，不先逐文件总结全仓库。依赖、生成文件和构建产物不宜计入业务规模；结合业务域、独立应用、模块关系及资料质量判断复杂度。记录实际项目或工作树位置和本次范围，初步地图保持可修正。

## 建议知识组织方式

| 形态 | 选择建议 |
| --- | --- |
| 单文件 | 业务集中、关系简单，用章节和锚点就能查找 |
| 多文件加索引 | 多个相对独立模块，需要按任务阅读局部背景 |
| 分层导航 | 多应用或多个大业务域，需要总入口和局部索引 |

主 Agent 说明选择理由和研究范围；后续材料表明结构不合适时再调整。无需先建完整目录，也不规定按代码量、文件数或行数强制拆分。

组织按阅读职责分工：总入口帮助选择项目或业务域，模块索引连接场景、职责与起读入口，专题解释模型、关系及关键边界，研究材料保留详细核验过程。它们可以是同一文件的章节，也可以按需要分文件；不以文件数量判断质量。总索引一行已需要密集罗列多个层次的路径时，保留主要起读点并链接局部说明，完整映射只在一个主要位置维护。

## 准备研究方式

CodeGraph 可用且已有项目索引时可复用；没有时建议用户选择安装、接入和建索引，或采用 Agent 扫描等其他方法。用户已经明确授权的操作按其范围执行；采用本指南本身不等于授权安装或修改客户端、仓库规则。

安装工具、接入客户端和为项目建立索引是不同操作。代码关系可以辅助核验，业务含义、黑话和选择原因仍需查拥有该事实的文档、讨论或向用户求证。需要安装来源时再读 [推荐小工具](recommended-tools.md)。

## 按职责研究

可根据初步地图有限并发分派子 Agent，已有依赖的主题分批处理。按业务职责切分，避免每个源码文件或目录都派一个 Agent；没有子 Agent 能力时，主 Agent 也可以按模块串行研究。

研究报告与正式知识分开保存。可在资料区的本次初始化需求目录下使用 `research/`，需求目录名称遵循目标项目的个人约束。每个任务保留研究问题、来源、结果和未完成项，便于中断后按需继续。

调研优先顺序为用途与场景、职责与对象、依赖与交互、代码与验证入口，最后提炼影响开发决策的重要规则。业务域研究可以包含多个功能模块，但返回结果应能区分各模块的职责和定位入口，避免只有一篇笼统的领域总结。

下面是可调整的任务提示词，借鉴 research 的一手证据与单份报告做法：

```text
研究模块：【业务域或功能模块】
项目位置：【本次仓库或工作树】
主 Agent 的初步认识：【职责假设、入口、关联模块】
待查问题与范围：【具体问题及相关资料】
报告位置：【本次研究目录及文件名】

优先查拥有该事实的一手资料，将关键结论追溯到需求、设计、源码或测试。
先说明谁在什么场景使用该模块、解决什么问题，再说明职责边界、核心对象和主要业务过程。
说明它从哪些内部模块或外部系统取得什么、向谁提供什么，以及数据/请求/事件的方向。
若涉及已确认且在范围内的跨仓库协作，返回提供方/消费方、关键契约或身份映射及可核验的对端入口；其他仓库的事实和权限边界分别说明。
找到并核验代表性代码入口，按实际形态说明页面/命令/任务、接口、核心逻辑、模型和测试各负责什么；不适用或未找到的入口如实说明。
代码路径使用明确的仓库相对路径，附职责和定位锚点。结合项目形态说明主要代码目录或文件组的职责范围，再给出少量代表入口；同一目录跨多个模块时解释划分依据，共享能力注明主要使用方。目录用于缩小候选范围，不将代码分层或目录名称直接当成业务归属证据。
有必要时研究生命周期、关键不变量、跨模块交互和重要决策原因。
区分已实现、设计计划、历史行为与未知内容，避免复制全部表、类和字段。
发现范围遗漏、概念冲突或跨模块问题时，返回依据交主 Agent 处理。
输出一份带来源的 Markdown 研究报告，返回业务摘要、模块与代码映射、依赖关系、报告路径和待核验事项。
仅写研究材料，不修改正式知识、业务代码或仓库规则，不安装工具。
```

## 主 Agent 综合、核验与建模

子 Agent 陆续回传后，主 Agent 可以边收集边整合，维护范围覆盖情况。报告提供候选结论；关键结论仍指向一手依据，不以其他 Agent 的总结替代最终来源。

推荐重点处理：重复知识、同义概念、模块职责和数据归属、跨模块交互、当前实现与文档计划的差异。疑问返回相关模块补查，不能靠猜测补齐。没有研究到的范围明确保留，不宣布已经完整覆盖。

先组织简短的项目业务主线与模块地图，再放主题细节。模块说明先让读者明白它做什么，再介绍易错边界；将只服务于研究复核的细节留在研究报告，避免初读被大量实现例外和未核验声明淹没。

正文优先保留职责、关系、关键不变量、非显而易见的限制及有来源的决策原因。默认数值、精确依赖版本、字段枚举等容易从单一事实源取得的信息，通常给配置或源码入口即可；某个具体值确实决定业务或协议兼容时再保留，并注明适用范围。研究细节不因已经查到就全部进入正式知识，也不为精简而删除会影响开发决策的边界。

依赖说明区分内部业务协作、运行基础设施与外部系统集成，说明谁使用它、用于什么、交互方向及不适用/未核验状态。只列技术栈版本或第三方包名不是依赖地图；是否必需、可选以及缺失后的影响只按实际证据描述。配置入口可以给出路径，不复制凭据或完整环境配置。

项目确实与其他仓库协作且属于本次研究范围时，按需说明本仓库提供或消费什么、交互方向、关键契约或身份映射，以及两边负责的实现或知识入口。同处父目录、名称相近或共享技术栈不证明业务依赖。对端未获准查看、不可访问或尚未核验时保留未知，仅给已知服务或仓库线索，不推断兼容性。

各项目只维护自己的职责和必要的协作摘要，对端细节引用其知识或代码，不复制整份正文、不创建父目录合并知识库。尽量使用适合当前分发范围的仓库标识和引用方式；本机路径仅标作本地定位线索，不作为通用可移植地址。无须为此建立全局项目注册表。发现对端可能需要更新时指出影响，不自动改写对端项目。

对有业务含义的模块提炼核心模型，解释概念是什么、归谁负责、彼此如何关联、生命周期和关键约束。状态、转换条件、历史原因等以实际证据为准。纯技术支撑模块可仅说明职责和依赖，无需为了完整性创造业务模型。

术语表解释名称、缩写和黑话；模型正文解释关系与业务规则。共享概念保留主要维护位置，相关模块引用它，避免各写一套相互矛盾的定义。

## 双向代码导航

单文件可用目录和锚点；多文件可用简短入口建立“模块 → 职责/模型/代码入口”“概念或别名 → 主要说明”“代码路径 → 所属模块/共享职责”的导航。以同一份模块—代码映射支持正反向查找，不维护两份容易漂移的完整副本。大项目在总入口保留领域摘要，再到局部模块索引，不把所有路径挤进首页。

代码导航保留足以开始任务的少量入口，说明每个入口负责什么；按项目实际形态选择页面、前端请求、服务接口、核心服务、领域模型、后台任务、代表性测试或 runbook。后端服务、CLI、库等没有页面时不用补造前端层。纯目录只能在职责足够明确时作为入口，扁平目录通常需要选代表文件。详细调用链和字段定义仍回源码。

可以用“模块｜职责与主要场景｜依赖/使用方｜关键代码入口及用途｜知识说明”组织映射；相关路径重叠时说明共享关系。路径明确到仓库内位置，知识文档中的相对链接应能从该文档实际位置解析；必要时附符号名作锚点，不仅写易混淆的短文件名、符号名或来源指纹。模板可参考 [知识便笺](../assets/templates/knowledge-note.md)，不是必填表格。

反向导航同时考虑已列出的入口和未逐一列出的相邻代码。职责明确的目录可作为模块范围；混合目录则用文件组、子目录或符号特征区分，并说明共享与交叉关系。按路径范围匹配得到的是模块候选，仍需结合代码职责确认；没有可靠匹配时说明缺口并进行任务级补查，不扩展成全仓逐文件索引。

## 用实际问题检查指引性

提交正式知识提案前，主 Agent 从本次覆盖范围选择有代表性的任务做导航走查，而不只检查链接存在。先循候选知识定位，再用源码核对落点；记录问题、知识阅读路径、代码落点与剩余缺口。无需执行应用或测试，也不以这次走查证明业务运行正确。

- **项目理解**：从入口能否说清服务对象、主要用途及一条业务主线？
- **业务找代码**：“我要修改某模块的一项行为”，能否找到模块说明、实际负责该行为的入口，以及需要关注的关联模块/验证入口？仅指向总路由表或整个 services 目录不算完成定位。
- **代码找业务**：结合项目形态，既检查已列出的代表入口，也从主要代码职责范围选择未单独列入索引的文件，判断能否缩小模块候选、解释职责并找到相关知识；混合目录或共享代码能否说明交叉关系及主要使用方？无法可靠归属时记录缺口，不要求每个源码文件都有索引。
- **依赖理解**：能否说明该模块依赖什么、为什么依赖、交互方向，以及哪些依赖状态尚未确认？
- **跨仓库任务（适用时）**：从一个真实协作变更问题出发，能否说清双方职责、契约或身份边界，并找到本仓库和可访问对端的负责入口？未核验对端实现时，不将单边理解当作兼容性已验证。

找不到落点、路径用途不匹配或仍需重新全仓扫描时，先补查并修订草案；暂时不能解决的缺口应明确留待确认，不能宣称该范围已经达到可导航标准。检查结果保存到本次需求的研究或验证资料，未覆盖部分仍保持原基线。

同时观察阅读成本：能否沿简短入口到相关专题和起读代码，而不必先读完所有模块或重新全仓扫描；是否为一个任务加载了明显无关的路径清单或重复正文。依据实际障碍调整导航，不规定固定跳转次数、读取文件数或量化分数。

## 展示与确认

展示组织方式、知识与模型草案、来源、已覆盖范围及待核验问题。正式写入复用 [提案与确认](proposals.md)，获准后应用，并检查入口和引用。大项目可按已经核验的主题分批审阅，保留其他区域的进度。

首次正式落库时，按目标项目的知识基线约束填写对应分支、完整提交哈希、实际写入时间（含时区）和覆盖范围；尚无约定时参照 [知识基线与更新时间](../assets/scaffold/constraints.md#知识基线与更新时间)。子 Agent 的研究结果也注明所依据版本；研究期间版本变化时先核对影响，不将不同版本的报告合并为“整库已同步”。

普通初始化预留的项目脚本和项目专属约束入口仍可供后续补充；缺少材料时保持空缺，不推测个人偏好或执行未知脚本。

## 后续维护

在明确启用 Compass 的任务中，发现知识缺失、概念变化或过期规则时，可以提示候选维护事项。用户明确请求同步或在任务中已经要求检查知识更新时，再按 `sync` 提案处理；正式修改仍经确认。

正文、术语、依赖和模块—代码映射一并考虑是否需要局部修订；路径迁移或职责变化可能值得维护导航，不等于记录每次实现改动。普通实现细节通常无需沉淀；未调用 Compass 的普通会话不自动进入知识维护。

用户明确要求按新版流程重做已有知识建设时，先评估现有资料，复用仍有效的知识和来源，只针对缺口补查并形成修订提案。不得先删除旧知识、覆盖个人约束或把旧批准用于新内容；需要重新组织的部分列入本次确认范围。普通重复 `init` 仍只补缺失骨架。
